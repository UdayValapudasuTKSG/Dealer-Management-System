# Reference R4 — RBAC & API/Error Conventions

This reference is the authoritative source for the permission vocabulary, the request-pipeline ordering, the HTTP status contract, idempotency semantics, and the cross-cutting API conventions (rate limiting, pagination, soft-delete/restore). Every other section that says **"see r4"** defers to the values stated here. State-machine values are owned by [r2](#r2); error *codes* are owned here.

## R4.1 Two-Plane Model & Request Pipeline

AURA exposes two portals over one API surface: the **Platform Console** (super-admin control-plane, `/platform/*` and `/admin/*`) and the **Dealer Workspace** (data-plane, dealer-scoped by `activeDealerId` resolved from the `x-dealer-id` header). Every data-plane request is evaluated by a fixed, ordered pipeline; the *first* failing stage determines the status code, and later stages never run.

| # | Pipeline stage | On failure | Notes |
| --- | --- | --- | --- |
| 1 | Authentication (session/JWT valid) | `401` | No/invalid/expired session. NEVER returned solely because `x-dealer-id` is absent (see R4.9 / NC-14). |
| 2 | Tenant resolution (`x-dealer-id` → active dealer) | See R4.9 | Header present but not in caller memberships → `403`. Header absent on a data-plane GET → default-dealer resolution or picker payload. Header unresolvable on a mutation → `400 dealer_required`. |
| 3 | Tenant lifecycle (dealer `status`) | `423` | Suspended tenant blocks data-plane *writes*; reads still allowed. See [r2](#r2) `dealers.status`. |
| 4 | RBAC authorization (module × category) | `403` | Role lacks the required `module:category` grant. See R4.3. |
| 5 | Entitlement / feature-flag gate | `404` | Runs *after* RBAC. Target module/agent not entitled for this dealer → hidden as not-found (INV-ENT-1, NC-9). Enforced server-side, never UI-only. |
| 6 | Rate limiting | `429` | Per-principal / per-dealer / per-IP quotas; emits `Retry-After`. See R4.6. |
| 7 | Idempotency check (mutations) | `409`/`422` | In-flight duplicate → `409`; key reuse with different body → `422 key_reuse_mismatch`. See R4.5. |
| 8 | Payload validation + stage gates | `422` | Zod schema failure, or unmet stage gate returning `{unmet:[]}`. |
| 9 | Resource resolution within active scope | `404` | Row not found *within the active dealer scope*. Foreign-tenant rows are hidden as `404` — NEVER `403`, so existence never leaks. |

Ordering rationale: RBAC (403) is evaluated before entitlement (404) so that a permitted-but-unentitled module is indistinguishable from a nonexistent one, while an unpermitted module is honestly denied. Cross-tenant isolation collapses to 404 at both stage 5 and stage 9.

## R4.2 HTTP Status Contract (canonical — NC-1)

The following is the complete, closed set of status codes AURA returns. No endpoint may introduce a code or meaning outside this table.

| Status | Meaning | Body / headers | When |
| --- | --- | --- | --- |
| `200` | OK — synchronous read or in-place mutation succeeded. | Resource or collection payload. Data-plane GET with no resolvable dealer returns the *picker payload* at 200 (not an error). | Reads; idempotent replays of a completed mutation (stored response returned at 200/201 as originally recorded). |
| `201` | Created — new resource persisted. | Created entity + `Location`. | POST that creates a row (e.g. lead, deal, quote, invoice, booking, service_case). |
| `202` | Accepted — async job enqueued. | `{jobId,status:"queued"}`. | Long-running / external-fanout actions: enquiry intake, booking *remind*, report/data *export*, outreach send. Result surfaces via notifications/webhook. |
| `400` | Malformed request OR unresolvable dealer on a mutation. | `{error:"dealer_required"}` for the tenant case. | Un-parseable body/params; mutation with no resolvable active dealer (NC-14). NOT used for schema-valid validation failures (those are 422). |
| `401` | No / invalid / expired session. | `WWW-Authenticate`. | Authentication stage only. NEVER returned merely because `x-dealer-id` is missing. |
| `403` | Authenticated but not permitted. | `{error, requiredPermission?}`. | RBAC denial (missing `module:category`) OR `x-dealer-id` present but NOT in caller memberships. NEVER used for a foreign-tenant *row* (that is 404). |
| `404` | Resource id not found *within active dealer scope*. | Generic not-found; no existence leak. | Unknown id, foreign-tenant row (isolation), or unentitled module/agent (NC-9). One code, three causes — indistinguishable by design. |
| `409` | Conflict — idempotency in-flight/duplicate OR write conflict. | `{error, conflict}`. | Duplicate `Idempotency-Key` still processing; optimistic-concurrency / version write conflict. |
| `422` | Unprocessable — validation, unmet stage gate, or key reuse mismatch. | `{error, unmet:[]}` for gates; `{error:"key_reuse_mismatch"}` for idempotency. | Zod/domain validation failure; stage-advance blocked by unmet checklist/gate; same `Idempotency-Key` replayed with a different body (NC-7). |
| `423` | Locked — tenant suspended. | `{error:"tenant_suspended"}`. | Data-plane *writes* blocked while `dealers.status = suspended`; reads still return 200. |
| `429` | Too many requests — rate limited. | `Retry-After` (seconds) + `RateLimit-*` headers. | Principal/dealer/IP quota exceeded. See R4.6. |

5xx codes are reserved for genuine server/infra faults and are out of the application-logic contract (see NC-12 honesty scope). External-dependency failures (GCS/SMTP/LOS) inside a SAGA surface as per-step failures with compensation, not as blanket 500s (see [r9](#r9), NC-11).

## R4.3 RBAC Module Vocabulary (canonical — NC-5)

Permissions are stored in `role_permissions` as `(module, category)` tuples and in `role_field_permissions` for field-level control. The module vocabulary below is closed — no endpoint may check a module key outside this list.

| Module key | Covers |
| --- | --- |
| `leads` | Leads, lead sources, assignment, advance, review, test-drive, outreach, agent-brief. |
| `customers` | Customers, contacts, overview, persona & persona/recommend, customer documents. |
| `deals` | Deals and deal stage progression (desking→committed→delivered). |
| `quotes` | Quotes, tax computation output, appraisals attached to quotes. |
| `bookings` | Bookings and booking reminders (soft-lock lifecycle). |
| `inventory` | Vehicles, assets, VIN allocation output, import. |
| `billing` | Invoices, payments, receipts (money-posting module). |
| `finance` | finance_applications, banks, LOS submissions. |
| `deliveries` | Deliveries and the 9-step delivery flow, PDI, delivery invoice PDF. |
| `service` | service_cases / service_orders, job_cards, service_invoices, coverage plans. |
| `parts` | Parts, suppliers, part_purchases, job_card_parts. |
| `gra` | GRA duty extraction/filings and the gra_filing gate workflow. |
| `reports` | Reports & BI (see [r5](#r5)). |
| `dashboard` | Dashboard widgets / KPIs. |
| `agents` | Agent catalog, runs, metrics (operational visibility — NOT kill-switch governance, see NC-13). |
| `communications` | Email/outbox, notifications, calls, WhatsApp conversations/messages. |
| `documents` | Documents and GCS-backed storage links. |
| `search` | Cross-entity search (dealer-scoped). |
| `settings` | Dealer settings, roles, taxes, divisions. |
| `platform` | Control-plane / super-admin operations (`/platform/*`, dealer provisioning). |
| `audit` | Audit-log read access (dealer-scoped). |

- **Action categories** (per module): `view` | `create` | `edit` | `delete` | `admin`. `admin` implies configuration/ownership of that module, not global superuser.
- **Field-level** (`role_field_permissions`): `hidden` | `view` | `edit`, overriding the module grant for named sensitive fields (e.g. floor price, cost, customer PII).
- **Governance is NOT an RBAC category.** The agent kill-switch is a platform-reserved `governance` capability, NOT grantable via `/admin/roles` and NOT equivalent to `settings:admin` (NC-13).

## R4.4 Impersonation Constraints (NC-10)

Super-admin impersonation of a dealer principal is **read-only by default**, time-boxed to **≤60 minutes**, reason-logged, and audited with `impersonatedBy` on every emitted record. Writes require explicit, logged elevation. The following are **hard-blocked** under impersonation even with elevation: money-posting (billing writes), gate resolution (`/gates/:id/resolve`), and any customer-facing send (outreach, WhatsApp, email). Attempts return `403` with an impersonation-block reason and are audited.

## R4.5 Idempotency (NC-7)

All mutating endpoints (POST/PUT/PATCH/DELETE) require an `Idempotency-Key` header. Keys are persisted in `idempotency_keys`, scoped to `(dealer, principal, route, key)`, with the request body fingerprint and the stored response.

| Scenario | Result |
| --- | --- |
| First use of key — succeeds | Response persisted against the key; returned verbatim on replay. |
| Replay of a *completed* request (same key, same body) | Stored response returned as originally recorded (200/201/202). |
| Duplicate while original is still *in flight* | `409` (idempotency in-flight/duplicate). |
| Same key, *different* body | `422 key_reuse_mismatch`. |
| Missing key on a mutation | `400` (malformed — key required). |

Idempotency keys are retained long enough to cover client retry windows; expiry does not resurrect a completed side effect because domain-level uniqueness (e.g. one active booking per vehicle) provides a second guard.

## R4.6 Rate-Limit Policy

Rate limiting runs at pipeline stage 6 (after entitlement). Limits are enforced per-principal, per-dealer, and per-source-IP; the tightest applicable bucket wins. Public / unauthenticated ingress endpoints carry stricter IP-based buckets.

| Class | Endpoints | Bucket | Default limit |
| --- | --- | --- | --- |
| Public ingress | WhatsApp/Meta LeadAds webhooks, Twilio voice/WhatsApp callbacks, Gmail intake, unauthenticated enquiry POST | Per source IP (+ signature verification) | Low burst; strict — abusive callers throttled early. |
| Authenticated read | Data-plane GET (lists, dashboards, search) | Per principal + per dealer | Generous; search/report reads on a tighter sub-bucket. |
| Authenticated write | Mutations (deals, invoices, gates, deliveries) | Per principal + per dealer | Moderate; idempotency absorbs retries. |
| Expensive async | Exports, outreach fan-out, agent runs, LOS sync, PDF generation | Per dealer | Low concurrency; queued at `202`. |

On breach the API returns `429` with:

- `Retry-After`: seconds until the caller may retry (REQUIRED on every 429).
- `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`: advisory window state so well-behaved clients self-pace.

Rate-limit counters are dealer-scoped so one tenant's traffic cannot exhaust another's quota. Message-broker-backed distributed limiting is PENDING-INFRA (NC-12); the current limiter is single-node.

## R4.7 Pagination Contract

All collection endpoints use **opaque cursor pagination** with a stable sort. Offset/limit paging is not offered (it drifts under concurrent inserts and leaks total-count timing).

| Element | Contract |
| --- | --- |
| Request params | `?cursor=<opaque>&limit=<n>`. `cursor` omitted → first page. |
| Max page size | `limit` clamped to a hard maximum of **100** (default 25). Values above the max are silently clamped, not rejected. |
| Stable sort | Deterministic ordering by `(sortKey, id)` — a tiebreaker on the immutable primary key guarantees no row is skipped or repeated across pages even when the sort field ties. |
| Response envelope | `{ data:[…], page:{ nextCursor:string\|null, hasMore:boolean } }`. `nextCursor:null` ⇔ `hasMore:false` ⇔ last page. |
| Cursor opacity | Cursor encodes the sort position + dealer scope; it is signed/validated. A cursor from a different dealer or tampered payload → `400` (malformed). |
| Total count | Not returned by default (avoids full scans); available only where an endpoint explicitly documents a `?withCount` option. |

Cursors are not durable bookmarks across schema/sort changes; a stale cursor that no longer resolves returns `400` and the client restarts from the first page.

## R4.8 Soft-Delete, Archive & Restore

Business entities are **soft-deleted**, never hard-removed from the data plane, preserving referential history and audit continuity. Deletion sets `deletedAt` / `deletedBy` (and, where modeled, an `archived` flag) within the active dealer scope.

| Action | Endpoint shape | RBAC | Effect |
| --- | --- | --- | --- |
| Soft delete / archive | `DELETE /api/<module>/:id` | `<module>:delete` | Sets `deletedAt`, `deletedBy`; row excluded from default lists and lookups. Idempotency-Key required (mutation). |
| Restore / un-archive | `POST /api/<module>/:id/restore` | `<module>:delete` (restore is a delete-class privilege) or `<module>:admin` where the module elevates it | Clears `deletedAt`/`deletedBy`; row returns to active state only if restore does not violate a live uniqueness/state invariant (else `422`). |
| Include deleted in reads | `GET …?includeDeleted=true` | `<module>:view` + audit-eligible | Returns soft-deleted rows with their deletion metadata; default reads exclude them. |

- **Scope & isolation:** a soft-deleted row is still dealer-scoped; a foreign-tenant id (deleted or not) resolves to `404`, never `403`.
- **Audit:** both delete and restore emit `audit_logs` entries and `timeline_events` with actor, reason (where provided), and before/after status. Restore is a first-class audited action, not a silent flag flip.
- **Impersonation:** delete/restore under impersonation follow R4.4 — allowed only with elevation, and blocked entirely where the row is a money-posting or gate record.
- **Immutable ledgers:** `payments` are an immutable ledger (see [r2](#r2)) — never soft-deleted; a reversal is an offsetting entry, and `invoices` are voided (status `void`), not deleted.
- **Tenant lifecycle:** delete/restore are data-plane writes → blocked with `423` while the dealer is `suspended`.

## R4.9 Missing / Foreign x-dealer-id Resolution (NC-14)

| Condition | Data-plane GET | Mutation |
| --- | --- | --- |
| Header absent | Default-dealer resolution: `lastActive` → sole membership → else return **picker payload at 200** (no error). | `400 dealer_required` if no active dealer resolvable. |
| Header present, in memberships | Scope to that dealer. | Scope to that dealer (subject to lifecycle/RBAC/entitlement). |
| Header present, NOT in memberships | `403`. | `403`. |

A missing header is NEVER, by itself, a `401`. Authentication (session) and tenant selection (dealer) are independent stages.

## R4.10 Error Body Shape

All non-2xx responses share a consistent envelope so clients can branch on a stable machine code rather than status alone.

- `{ error: "<machine_code>", message: "<human readable>", … }`
- Contextual fields as documented above: `unmet:[]` (422 stage gate), `requiredPermission` (403 RBAC), `retryAfter` mirrored in `Retry-After` (429), `conflict` (409).
- Canonical machine codes referenced by this spec: `dealer_required` (400), `tenant_suspended` (423), `key_reuse_mismatch` (422). Not-found is intentionally generic (no existence leak).
