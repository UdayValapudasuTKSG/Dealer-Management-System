# Reference R2 — State Machines

This section is the **single source of truth** for every lifecycle enum in AURA. All other sections (`r1`, `r3`–`r10`, `X*`, `V*`) *reference* these values via "see r2" and MUST NOT restate alternative states, orderings, or terminal names. Where a machine name maps to a physical column it is noted; UI pipeline labels (**§R2.12**) are presentation-only and are NOT database enums. Transitions are dealer-scoped: every guard implicitly requires the row to resolve within the active dealer scope (a foreign row is invisible → `404`, never `403`; see r4/NC-1). Suspended tenants (`dealers.status=suspended`) block all data-plane *write* transitions with `423` while reads remain allowed.

## R2.0 Conventions

- **Terminal states** are absorbing — no outbound transitions. They are listed explicitly per machine.
- **Who transitions** distinguishes: *human* (RBAC-gated actor), *SYSTEM* (deterministic plain-code action inside the transactional flow: A2 `round_robin`, A3 `quote_tax`, A11 `vin_allocation` — NOT kill-switchable, NOT "AI writes"), and *autonomous AI writer* (A1 `intake_dedup`, A6 `call_sentiment`, A16 `case_classifier` — audited, kill-switchable). HITL/advisory agents (A5, A7, A10, A15, etc.) never drive a state transition without human confirmation. See r3/NC-6.
- **Gate-guarded** transitions cannot complete while an `open` blocking gate of the relevant type exists; the attempt returns `422 {unmet:[...]}`. Canonical gate types (exactly 6): `below_floor_price`, `credit_decline`, `capital_order`, `gra_filing`, `refund_release`, `stage_advance` (see r2/§R2.11 and NC-4). VIN allocation is NOT a gate.
- All mutating transitions require an `Idempotency-Key` (NC-7): completed replay → stored response; in-flight duplicate → `409`; same key + different body → `422 key_reuse_mismatch`.
- Every transition emits a `timeline_events` row and, for privileged/money/gate actions, an `audit_logs` row.

## R2.1 lead.phase (leads)

**States:** `new` → `contacted` → `qualified` → `proposal` → `negotiation` → `won` | `lost`. **Terminal:** `won`, `lost`. Linear forward path with the two terminal branches; `lost` is reachable from any non-terminal phase (disqualify/drop).

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `new` | Source resolved (`lead_sources`); dealer scope resolvable else `400 dealer_required` | Human (leads:create) or SYSTEM ingest (WhatsApp/LeadAds/Gmail intake) | A1 `intake_dedup` (autonomous) runs: merge/flag duplicate; A2 `round_robin` (SYSTEM) assigns owner; timeline event |
| `new` → `contacted` | At least one logged outbound touch (`call_logs`/WhatsApp/email) | Human (leads:edit); A7 outreach is Approve&Send (HITL) | A6 `call_sentiment` may annotate calls; notification per r6 |
| `contacted` → `qualified` | Qualification fields complete (budget/intent/contact) | Human (leads:edit) | Enables proposal/quote actions; A15 `pipeline_suggestions` advisory only |
| `qualified` → `proposal` | ≥1 quote generated (A3 `quote_tax` deterministic pricing) | Human (leads:edit / quotes:create) | Quote(s) attached; test_drives may be scheduled (A10 advisory) |
| `proposal` → `negotiation` | Customer counter/active discussion | Human (leads:edit) | Discount discussion may later raise `below_floor_price` gate at deal commit |
| `negotiation` → `won` | Deal created & committed (see r2/§R2.2 `deal.stage=committed`) | Human (leads:edit + deals:create) | Creates/links `deals`; A11 `vin_allocation` locks VIN on commit; customer promoted |
| any non-terminal → `lost` | Reason captured | Human (leads:edit) | Frees any soft-locked vehicle (`reserved`→`available`); closes open tasks |

## R2.2 deal.stage (deals)

**States:** `desking` → `committed` → `delivered` (+ `cancelled` | `lost`). **Terminal:** `delivered`, `cancelled`, `lost`. The *human* decision is the commit; VIN allocation follows deterministically (no separate AI/VIN gate).

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `desking` | Customer + vehicle selection; quote priced (A3) | Human (deals:create) | Vehicle may move to `reserved` (soft-lock) for booking/test-drive |
| `desking` → `committed` | **Gate-guarded:** if discount below floor, `below_floor_price` gate must be `resolved(approve)`; if capital order, `capital_order` gate resolved; else `422 {unmet:[]}` | Human commit (deals:edit/admin) resolves gate; A11 `vin_allocation` (SYSTEM) then runs in-transaction | VIN locked → vehicle `reserved`→`booked`; booking may convert; invoice issuance enabled; audit_log |
| `committed` → `delivered` | Delivery SAGA complete (all 9 delivery steps; see r2/§R2.9); invoice `paid` or approved finance disbursed | Human (deliveries:edit) — final delivery step | Vehicle `booked`→`delivered`→`sold`; lead → `won`; reviews (CSAT) invited |
| `desking`/`committed` → `cancelled` | Pre-delivery cancellation; if money posted, `refund_release` gate resolved | Human (deals:admin) | Compensation: VIN released (`booked`→`available`), booking `cancelled`, offsetting payment entries |
| `desking` → `lost` | Lost to competitor/no-deal (pre-commit) | Human (deals:edit) | Frees soft-lock; lead may go `lost` |

## R2.3 vehicle.status (vehicles)

**States:** `in_transit` → `available` → `reserved` → `booked` → `delivered` → `sold` (+ `service`, `under_repair`). `reserved` = test-drive/booking soft-lock; `booked` = allocated to a *committed* deal. The term "allocated" is NEVER used as a status. `service`/`under_repair` are side branches reachable from `available` (or post-`sold` service intake) and return to `available`.

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (import) → `in_transit` | Vehicle imported (VIN/engine 17-char); not yet on-lot | Human (inventory:create / import) | Not sellable; excluded from availability |
| `in_transit` → `available` | Received on-lot / PDI-ready | Human (inventory:edit) | Appears in availability-check (A10 advisory) |
| `available` → `reserved` | Test-drive or booking soft-lock (`bookings.status=active`) | Human (bookings:create / test_drives) | Excluded from other reservations; auto-release on booking expiry |
| `reserved` → `booked` | Deal committed → A11 `vin_allocation` deterministically locks this VIN | SYSTEM (A11) in commit transaction | Hard allocation to the committed deal; booking `converted` |
| `booked` → `delivered` | Delivery step `delivery`/`signature` reached | Human (deliveries:edit) | Physical handover recorded |
| `delivered` → `sold` | Delivery SAGA closed (feedback step), title transferred | SYSTEM on delivery completion | Removed from active inventory; deal → `delivered` |
| `reserved`/`booked` → `available` | Booking expired/cancelled or deal cancelled (compensation) | Human / SYSTEM saga compensation | Soft/hard lock released |
| `available` ↔ `service` / `under_repair` | Service intake / repair need | Human (service:edit / inventory:edit) | Temporarily non-sellable; returns to `available` when resolved |

## R2.4 booking.status (bookings)

**States:** `active` → `converted` | `expired` | `cancelled`. **Terminal:** `converted`, `expired`, `cancelled`.

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `active` | Vehicle `available`; deposit/hold recorded | Human (bookings:create) | Vehicle → `reserved`; remind action available (202 async) |
| `active` → `converted` | Associated deal committed (A11 locks VIN) | SYSTEM on deal commit | Vehicle `reserved`→`booked` |
| `active` → `expired` | Hold window elapsed without conversion | SYSTEM (scheduled) | Vehicle `reserved`→`available`; notification per r6 |
| `active` → `cancelled` | Manual cancellation; refund via `refund_release` gate if deposit posted | Human (bookings:edit/admin) | Vehicle released; offsetting payment entry if refund |

## R2.5 finance_applications.status (finance_applications)

**States:** `pending` → `submitted` → `under_review` → `approved` | `declined` → `disbursed`. **Terminal:** `declined`, `disbursed`. Integration with LOS Demerara (live/sandbox) via `los_submissions`; never hold a DB transaction across the LOS call (SAGA, NC-11).

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `pending` | Applicant + bank selected; docs collected (A5 doc_prefill HITL) | Human (finance:create) | Draft application; nothing sent externally |
| `pending` → `submitted` | Required fields/docs complete | Human (finance:edit) via /submit | SAGA step: LOS submission created (durable marker); 202 async |
| `submitted` → `under_review` | LOS acknowledged (sync/webhook) | SYSTEM (los sync) | `los_submissions` updated; timeline |
| `under_review` → `approved` | LOS decision = approve | SYSTEM (los sync) | Enables disbursement path |
| `under_review` → `declined` | LOS decision = decline | SYSTEM (los sync) | Raises `credit_decline` gate for human handling; notification |
| `approved` → `disbursed` | Funds released to deal; money-posting recorded | Human (billing/finance admin) — HARD-BLOCKED under impersonation | Payment ledger entry; enables deal delivery |

## R2.6 invoices.status (invoices)

**States:** `issued` → `partially_paid` → `paid` → `void`. There is **NO `draft`** state. **Terminal:** `paid` (settled), `void`. Money is USD-scale, displayed in GYD via `usdExchangeRate` (~209); no payment gateway — payments are recorded manually.

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `issued` | Deal committed; line items + taxes computed (A3 `quote_tax`, dealer_taxes) | Human (billing:create) — HARD-BLOCKED under impersonation | Invoice PDF (pdfkit, r8); outstanding balance updated |
| `issued` → `partially_paid` | Payment(s) < total recorded | Human (billing:create payments) / receipts | Immutable payment ledger entry; receipt issued |
| `partially_paid` → `paid` | Cumulative payments ≥ total | Human (billing) / SYSTEM balance calc | Marks settled; enables delivery invoice step |
| `issued` → `paid` | Single full payment | Human (billing) | As above |
| `issued`/`partially_paid` → `void` | Cancellation/correction; `refund_release` gate if refunding posted money | Human (billing:admin) — HARD-BLOCKED under impersonation | Offsetting (reversal) ledger entries — payments never mutated |

## R2.7 service_orders.status (the Case)

**States:** `open` → `acknowledged` → `in_progress` → `on_hold` → `resolved` → `closed` (+ `cancelled`). **Terminal:** `closed`, `cancelled`. This is the dedicated Case machine. (Corrected design promotes a dedicated `service_cases` table; the built app reused `service_orders` — see r9/X1.)

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `open` | Customer/vehicle linked | Human (service:create) / SYSTEM intake | A16 `case_classifier` (autonomous) categorizes/routes |
| `open` → `acknowledged` | Assigned/triaged | Human (service:edit) | SLA clock start; notification |
| `acknowledged` → `in_progress` | Work begun; job_cards opened (see r2/§R2.8) | Human (service:edit) | Job cards + parts consumption |
| `in_progress` ↔ `on_hold` | Awaiting parts/customer/approval | Human (service:edit) | SLA pause; can resume to `in_progress` |
| `in_progress` → `resolved` | All job_cards `completed`; service invoice issued | Human (service:edit) | reviews (CSAT) invited; service_invoice |
| `resolved` → `closed` | Customer confirmation / settlement | Human (service:edit) / SYSTEM auto-close | Timeline close |
| any non-terminal → `cancelled` | Withdrawn / duplicate | Human (service:admin) | Reverses open job_cards; releases held parts |

## R2.8 job_cards.status (job_cards)

**States:** `open` → `in_progress` → `on_hold` → `completed` → `closed` (+ `cancelled` for withdrawn cards). **Terminal:** `closed`, `cancelled`. A job_card belongs to a parent service_order/Case.

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `open` | Parent case `acknowledged`/`in_progress` | Human (service:create) | Labor lines drafted |
| `open` → `in_progress` | Technician assigned; work started | Human (service:edit) | `job_card_parts` reserved; parts stock decremented |
| `in_progress` ↔ `on_hold` | Awaiting parts (part_purchases)/approval | Human (service:edit) | Resume to `in_progress` |
| `in_progress` → `completed` | Work finished; parts/labor finalized | Human (service:edit) | Feeds service_invoice; parent case can resolve |
| `completed` → `closed` | Billed/settled | Human / SYSTEM | Timeline close |
| `open`/`in_progress` → `cancelled` | Withdrawn | Human (service:admin) | Releases reserved parts |

## R2.9 deliveries.step — the 9-step delivery SAGA (deliveries)

**EXACTLY 9 steps** (label it "9-step", never "9-step"), advanced in order via `deliveries/advance`: `sales_order` → `pdi_checklist` → `registration` → `insurance` → `invoice` → `appointment` → `delivery` → `signature` → `feedback`. Implemented as a SAGA with durable per-step markers and per-step compensation; NEVER hold a DB transaction across an external call (GCS/SMTP/registration/insurance). Advancing past a step whose prerequisites are unmet returns `422 {unmet:[...]}`; a `stage_advance` gate may guard privileged advancement.

| # | Step | Guard / prerequisite | Who | Side-effects & compensation |
| --- | --- | --- | --- | --- |
| 1 | `sales_order` | Deal `committed`; VIN `booked` (A11) | Human (deliveries:edit) | Sales order recorded; comp: revert to desking on cancel |
| 2 | `pdi_checklist` | Pre-delivery inspection complete (`stage_checklists`) | Human (deliveries:edit / service) | Checklist persisted; comp: reopen checklist |
| 3 | `registration` | Registration `^[A-Z]{3}[0-9]{1,4}$`; external registry step (no DB txn held) | Human (deliveries:edit) | Durable marker; comp: void registration record |
| 4 | `insurance` | Insurance policy attached | Human (deliveries:edit) | Document stored (GCS presigned); comp: detach |
| 5 | `invoice` | Invoice `paid` or approved finance `disbursed` | Human (billing/finance) | invoice.pdf (r8); comp: void invoice via refund_release |
| 6 | `appointment` | Delivery slot scheduled | Human (deliveries:edit) | Notification per r6; comp: cancel appointment |
| 7 | `delivery` | Physical handover; steps 1–6 done | Human (deliveries:edit) | Vehicle `booked`→`delivered`; comp: recall |
| 8 | `signature` | Customer acceptance captured | Human (deliveries:edit) — customer-send HARD-BLOCKED under impersonation | Signed doc stored; comp: reopen |
| 9 | `feedback` | CSAT/reviews invited | Human / SYSTEM | Vehicle `delivered`→`sold`; deal → `delivered`; reviews (CSAT) created |

## R2.10 gates.status (gates)

**States:** `open` → `resolved`, where resolution carries a decision `approve` | `reject` (i.e., `resolved(approve|reject)`). **Terminal:** `resolved`. An `open` gate blocks its guarded transition (`422 {unmet:[...]}`). Gate resolution is a money/authority action → HARD-BLOCKED under impersonation (NC-10); resolution is a platform/RBAC-authorized human action, audited.

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (raise) → `open` | Triggering condition met (see gate types below) | SYSTEM (deterministic) / advisory agent surfacing | Blocks target transition; notification per r6 |
| `open` → `resolved(approve)` | Authorized approver; via `gates/resolve` | Human (relevant module admin) — not impersonation | Unblocks guarded transition; audit_log |
| `open` → `resolved(reject)` | Authorized approver | Human | Guarded transition denied; upstream state may revert/lost |

**Canonical gate types (exactly 6, NC-4):** `below_floor_price` (deal commit under floor), `credit_decline` (LOS declined), `capital_order` (capital/large-order approval), `gra_filing` (Guyana Revenue Authority filing — `gra_extract` supplies legible fields only; human files), `refund_release` (refund of posted money), `stage_advance` (privileged stage advancement). Document-HITL and agent-run approvals are **INLINE REVIEWS, not gates**. VIN allocation is NOT a gate (deterministic on deal commit via A11).

## R2.11 dealers.status (dealers — control-plane)

**States:** `provisioning` → `active` → `suspended` → `offboarding` → `closed`. Create returns `provisioning`; go-live checklist completion → `active`. `suspended` blocks data-plane *writes* (`423`) but allows reads. Provisioning is a SAGA (NC-11) with durable per-step markers and compensation; status stays `provisioning` until complete.

| From → To | Guard | Who | Side-effects |
| --- | --- | --- | --- |
| (create) → `provisioning` | Platform-console create; SAGA started | Super-admin (platform) | Tenant scaffolding; not yet write-live |
| `provisioning` → `active` | Go-live checklist complete; all SAGA steps durable | Super-admin (platform) | Data-plane opened; entitlements applied (INV-ENT-1) |
| `active` → `suspended` | Billing/compliance/manual hold | Super-admin (platform) | Data-plane writes → `423`; reads allowed |
| `suspended` → `active` | Hold cleared | Super-admin (platform) | Writes restored |
| `active`/`suspended` → `offboarding` | Termination initiated | Super-admin (platform) | Export/retention per r10; winding down |
| `offboarding` → `closed` | Retention window elapsed; data-subject obligations met (r10) | Super-admin (platform) | Terminal; tenant sealed |

## R2.12 UI Pipeline Labels → (lead.phase + deal.stage) mapping

The Dealer Workspace pipeline board shows 8 **presentation-only** labels: *New, Contacted, Engaged, Pre-Book, Vehicle Allocated, Payment, Pre-Delivery, Delivered*. These are NOT a database column — they are a projection over the canonical `lead.phase` and `deal.stage` enums (and, downstream, `vehicle.status`/`invoices.status`/`deliveries.step`). Treat the labels strictly as a view.

| UI pipeline label | Maps onto `lead.phase` | Maps onto `deal.stage` / downstream signal |
| --- | --- | --- |
| New | `new` | — |
| Contacted | `contacted` | — |
| Engaged | `qualified`, `proposal`, `negotiation` | deal not yet `committed` (`desking`) |
| Pre-Book | `negotiation` / `won` | `desking` with active booking (`booking.status=active`, vehicle `reserved`) |
| Vehicle Allocated | `won` | `committed` — VIN locked, vehicle `booked` (label says "Allocated" but the status is `booked`, never "allocated") |
| Payment | `won` | `committed`; `invoices.status` ∈ {`issued`,`partially_paid`} or finance `under_review`/`approved` |
| Pre-Delivery | `won` | `committed`; delivery SAGA steps 1–8 (`sales_order`…`signature`) in progress |
| Delivered | `won` | `delivered`; delivery step `feedback`; vehicle `sold` |

*Lost/cancelled* outcomes (`lead.phase=lost`, `deal.stage=cancelled|lost`) are rendered as a separate off-pipeline bucket, not as a board column.
