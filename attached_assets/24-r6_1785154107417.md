# Reference R6 — Notifications & Comms Matrix

Every notification in AURA is **dealer-scoped** (persisted with `dealerId`, filtered by `activeDealerId(res)` + `x-dealer-id`). **In-App is always the primary channel** — a row is written to `notifications` for the target `dealer_users` record and rendered via `GET /api/notifications`. Email and WhatsApp are **supplementary, opt-in, best-effort** channels that flow through the unified OUTBOX (`email_logs`, one table for both email and WhatsApp with `channel` discriminator) and the retry/backoff worker. Recipient resolution never trusts request-body role claims; it derives role from `role_permissions` / `dealer_users` (`reportingManagerUserId`, `divisionId`, `isGeneralManager`). All customer-facing message bodies that echo user/AI text are wrapped with `guardUntrusted` before templating. Any notification originating from an autonomous agent carries `isAgent = true` on its `timeline_events` row and a linked `agent_runs` record.

## R6.1 Channel & delivery model

| Channel | Store / mechanism | Delivery guarantee | Dedupe / idempotency | Failure behavior |
| --- | --- | --- | --- | --- |
| **In-App (primary)** | Row in `notifications` (per `dealer_users`), surfaced by `GET /api/notifications`; unread badge | Synchronous DB write inside the triggering transaction — never lost, never retried | Natural key `(dealerId, recipientUserId, type, entityType, entityId)`; upsert bumps `updatedAt` instead of duplicating | N/A (transactional). If parent txn rolls back, no notification. |
| Email | `email_logs` OUTBOX (`channel='email'`), rendered from `emails/templates`, sent by nodemailer Gmail SMTP worker | At-least-once via DB outbox; `emails/settings` per dealer can disable | `dedupeKey` unique per logical event; worker skips already-`sent` keys | Exponential backoff, capped attempts; `POST /api/emails/logs/:id/retry` for manual replay; terminal → `status='failed'` |
| WhatsApp | `email_logs` OUTBOX (`channel='whatsapp'`) → Meta Cloud API v21 / Twilio adapter; conversation state in `whatsapp_conversations`/`whatsapp_messages` | At-least-once; requires opt-in + open 24h session or approved template | `dedupeKey` as below; outbound linked to `whatsapp_conversations.id` | Backoff retry; on hard failure or opt-out → **fallback to Email, then In-App only** (see R6.4) |

## R6.3 dedupeKey construction rules

- Every OUTBOX (`email_logs`) row carries a `dedupeKey`; the worker treats an already-`sent` key as a no-op, making all senders idempotent under retries and duplicate triggers (e.g. webhook redelivery, sweep overlap).
- Keys are **event-scoped, not time-scoped**, except recurring nudges which append a bounded index/window suffix (`:remind:{n}`, `:{dueWindow}`) so each legitimate reminder is distinct but the count is capped.
- Advisor and manager copies of the same underlying event use **distinct keys** (suffix `:advisor`/`:manager`) so both are delivered rather than one deduping the other.
- In-App notifications dedupe on the natural key `(dealerId, recipientUserId, type, entityType, entityId)` — a repeat trigger bumps `updatedAt`/unread rather than stacking rows.
- All keys are implicitly dealer-partitioned; `dealerId` is part of the stored row scope so identical entity ids across dealers never collide.

## R6.4 WhatsApp opt-out & delivery-failure fallback

| Condition | Detection | Action | Persistence |
| --- | --- | --- | --- |
| **Explicit opt-out** | Inbound STOP/unsubscribe keyword on `webhooks/whatsapp` or `webhooks/twilio/whatsapp`, or preference cleared on `contacts`/`customers` | Suppress all future WhatsApp sends to that number; downgrade every WhatsApp row for that recipient to **Email → In-App** | Opt-out flag on `contacts`/`whatsapp_conversations`; audited |
| No prior opt-in | No consent record / no session in `whatsapp_conversations` | Do not initiate WhatsApp; use Email (if valid) else In-App only. Customer-facing content still delivered | Consent state on contact record |
| Outside 24h session window | Last inbound > 24h ago in `whatsapp_conversations` | Only pre-approved Meta templates may send; free-form composed messages (A7 outreach) queue until session reopens or route to Email | `whatsapp_messages` window state |
| **Delivery failure** (transient) | Provider error / no delivery receipt; `email_logs` attempt fails | Exponential backoff retry up to cap; `POST /api/emails/logs/:id/retry` for manual replay | Attempt count + status on `email_logs` |
| Delivery failure (terminal) | Retry cap reached or hard bounce/invalid number | **Cascade: WhatsApp → Email → In-App**. Re-enqueue the same logical event on the next channel with a new channel-suffixed `dedupeKey` (`...:fallbackEmail`) so it is not deduped against the failed WhatsApp send | `email_logs.status='failed'`; fallback row linked; advisor In-App notice on customer-facing failure |

In-App is never subject to opt-out or delivery failure — it is the guaranteed floor for every trigger, so a customer opting out of WhatsApp and lacking a valid email still leaves the internal recipient (advisor/manager) fully notified, and vice-versa. Fallback cascades are dealer-scoped and audited via `activity`/`timeline_events`.
