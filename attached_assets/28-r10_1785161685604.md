# Reference R10 — Privacy, Retention & Data-Subject Rights

This reference defines how AURA captures marketing consent, honors per-customer data-subject rights *within a single LIVE tenant*, classifies and retains personal data, and purges/anonymizes it. It is the authoritative source for privacy semantics; other sections reference it as **see r10**. Data-subject operations are ordinary data-plane actions, dealer-scoped by `activeDealerId`+`x-dealer-id`, and therefore inherit every tenant-isolation status code in **r4** (`401`/`403`/`404`/`409`/`422`/`423`/`429`). Whole-tenant lifecycle (offboarding/closed) is **P3**, separate from the per-customer rights below and cross-referenced in §R10.9.

## R10.1 Scope, posture & honesty boundary

- **Jurisdiction.** Dealers operate in Guyana (CAM/GT). AURA's privacy design aligns to the principles of the Guyana *Data Protection Act 2023* — lawful basis, purpose limitation, data minimization, accuracy, storage limitation, and data-subject access/erasure/rectification — and follows GDPR-style best practice where the local Act is silent. AURA does not assert legal certification; it implements the application-logic controls that make compliance operable.
- **Controller/processor.** Each dealer is the *data controller* for its customers; AURA (the platform) is the *processor*. Consent, retention overrides, and DSR fulfillment are the dealer's responsibility; AURA provides the tooling, audit trail, and enforcement.
- **Honesty scope (see **NC-12**/r9/V4).** "Foolproof" here means application-logic correctness of consent gating, PII anonymization, and audit. Propagation of erasure to *backups, replicas, and DR snapshots* is **PENDING-INFRA** — those NFRs (backup/DR, encryption-at-rest) are pre-GA blockers tracked in V4, not claimed as production-ready. Live-database erasure is enforced today; backup propagation activates when that infra lands (§R10.7).
- **Guyana-computed, no fabrication.** Consistent with GRA duty handling, AURA never fabricates identity or regulatory data; national-ID and financial fields are captured as provided and anonymized (not deleted) where audit obligations conflict with erasure.

## R10.2 PII classification

Every field mapped in **r1** carries a classification tag that drives export scope, erasure behavior, and field-level RBAC (`hidden|view|edit`, see **r4**).

| Class | Examples (r1 tables/fields) | Erasure behavior | Default field-perm floor |
| --- | --- | --- | --- |
| **C1 — Direct identifier** | `customers.fullName`, `contacts.phone`, `contacts.email`, national-ID/TIN, `leads` contact fields | Anonymize (tokenize/redact) | `view` for customers:view; `edit` gated |
| **C2 — Quasi-identifier** | address, DOB, vehicle plate `^[A-Z]{3}[0-9]{1,4}$`, VIN(17) tied to owner | Anonymize or generalize | `view` |
| **C3 — Sensitive / financial** | `finance_applications`, `los_submissions`, `invoices`, `payments`, `receipts`, appraisal values | **Retain** (audit/legal) — de-link identity, keep amounts | billing/finance module RBAC |
| **C4 — Communications content** | `whatsapp_messages`, `call_logs`/transcripts, `email_logs`, `timeline_events` notes, `call_sentiment` output | Purge on retention or on erasure | communications module RBAC |
| **C5 — Derived / behavioral** | persona, `pipeline_suggestions`, `agent_runs` prompts/outputs, CSAT `reviews` | Purge payloads; keep aggregate metrics | agents/reports RBAC |
| **C0 — Non-personal / operational** | config, `dealer_taxes`, `usdExchangeRate`, part SKUs | Not in DSR scope | module default |

## R10.3 Consent capture & marketing opt-in / opt-out

- **Web-to-lead.** The Meta Lead Ads / web intake path (see **r7**) records a per-channel `marketingConsent` object on the created `lead`/`customer`: `{channel, granted:bool, basis, capturedAt, sourceEvent}`. Consent is captured at submission; absence of explicit grant defaults to `granted:false` (opt-in, not opt-out). The A1 `intake_dedup` autonomous writer must **carry consent forward on merge** — never upgrade a merged record's consent from any source.
- **WhatsApp opt-in / opt-out.** Meta/Twilio WhatsApp (see **r7**) requires a stored opt-in before any outbound template. Inbound `STOP`/opt-out keywords set `whatsapp_conversations.optOut=true` immediately and idempotently; subsequent outbound sends (including A7 `outreach` Approve&Send and `bookings/remind`) are hard-suppressed at send time, returning a suppressed disposition, not an error. Re-opt-in requires a fresh inbound consent event. Opt-out is enforced server-side, independent of any UI toggle.
- **Notification interplay (see **r6**).** Transactional/service notifications tied to an active deal/delivery are lawful-basis "contract" and are NOT suppressed by *marketing* opt-out; only marketing-class outreach is. The notifications matrix flags each row's consent class.
- **Agent gating.** A7 `outreach`, `persona_recommend`, and `pipeline_suggestions` read consent and opt-out before proposing sends; all remain HITL/advisory (see **r3**) and honor `isAgentEnabled(...)` kill-switches.

## R10.4 Data-subject rights (within a LIVE tenant)

| Right | Endpoint | Semantics | Success code |
| --- | --- | --- | --- |
| Access / Export (portability) | `GET /api/customers/:id/export` | Assembles all classes C1–C5 for the customer within active dealer scope into a portable bundle (JSON + attached docs via GCS presigned). Long-running → queued. | `202` accepted async (see **NC-1**; export is an async class), artifact fetched via presigned URL on completion |
| Erasure (right to be forgotten) | `POST /api/customers/:id/erase` | Anonymizes C1/C2, purges C4/C5 payloads, **retains C3 financial rows with identity de-linked** (see §R10.5). Mutation → requires `Idempotency-Key`. | `202` accepted async (saga, §R10.5) or `200` stored replay |
| Rectification | `PATCH /api/customers/:id` (+ `/contacts`) | Correct inaccurate C1/C2 fields; validation per **r4**; timeline event + audit written. | `200` |
| Restriction / objection | consent + opt-out toggles (§R10.3) | Suppress marketing processing without erasing the record. | `200` |

| Code | When (on export/erase/rectify) |
| --- | --- |
| `401` | No/invalid session. Never returned merely for a missing `x-dealer-id` (NC-14). |
| `403` | Authenticated but RBAC-denied, OR `x-dealer-id` not in caller memberships. |
| `404` | Customer id not found *within active dealer scope* — this hides foreign-tenant customers with no existence leak (never `403` for a foreign row). Also returned when the privacy/DSR feature is not entitled for the dealer (NC-9, INV-ENT-1). |
| `409` | Erasure already in-flight for this key, or duplicate; also write-conflict if the customer mutated mid-saga. |
| `422` | Validation error; `{unmet:[]}` if an unmet gate/legal-hold blocks erasure; `key_reuse_mismatch` on same key + different body. |
| `423` | Tenant suspended → **erase/rectify (data-plane writes) blocked**; `export` (read) still permitted. |
| `429` | Rate limited (+ `Retry-After`). |
| `400` | Mutation with no resolvable active dealer → `dealer_required` (malformed/unresolvable dealer on a write). |

Missing `x-dealer-id` on the `GET .../export` (data-plane read) triggers default-dealer resolution (lastActive → sole membership → else picker payload `200`); it is never a `401` (NC-14).

## R10.5 Erasure mechanics — anonymize vs. purge vs. retain

- **Anonymize (C1/C2).** `fullName`→`"Erased Subject <token>"`, `phone`/`email`→null-tokenized, national-ID/TIN→hashed-or-nulled, address generalized. The customer row survives as a shell so referential integrity to financial rows holds.
- **Purge (C4/C5).** `whatsapp_messages`, `call_logs`/transcripts, `email_logs` bodies, `timeline_events` free-text notes, `agent_runs` prompt/output payloads, `reviews` free-text, and OCR text (`gra_extract`) are deleted or redacted. Aggregate metrics (counts, CSAT score without comment) are retained.
- **Retain, de-identified (C3).** `invoices`, `payments` (immutable ledger — reversal is an offsetting entry, never a delete, see **r2**), `receipts`, `finance_applications`, `los_submissions`, and appraisal amounts are *kept* for audit/tax/GRA obligations with the identity link severed to the anonymized shell. Erasure never rewrites the payments ledger.
- **Legal-hold override.** If an open deal/finance app/gate or an active statutory retention (e.g. tax) applies, erasure is deferred and the endpoint returns `422 {unmet:[...]}` listing the holds; the request is queued for post-hold execution rather than silently ignored.
- **SAGA execution (see **NC-11**).** Erasure spans DB rows + external stores (GCS documents), so it runs as a durable multi-step saga with per-step markers and per-step compensation. **Never** hold a DB transaction across the GCS delete call. Steps: (1) freeze/consent-flag, (2) anonymize C1/C2, (3) purge C4/C5, (4) de-link + retain C3, (5) delete GCS document objects, (6) enqueue backup-propagation marker (§R10.7), (7) finalize + audit. Each step is idempotent; failure compensates and the key remains replayable.

## R10.6 Retention windows & purge jobs

Retention is enforced by scheduled archival/purge jobs (server-side, dealer-scoped). Windows below are defaults; a dealer may extend (never shorten below a statutory floor). Audit is exempt from data-subject erasure.

| Data class (r1) | Default retention | Job action at expiry | DSR-erasable? |
| --- | --- | --- | --- |
| `audit_logs` | 7 years (statutory floor) | Archive to cold store; never auto-purged before floor; immutable | **No** — retained for integrity/accountability even after subject erasure |
| `call_logs`/transcripts & `timeline_events` notes (comm-notes, C4) | 24 months | Purge transcript/body text; keep call metadata (duration, direction) | Yes |
| `agent_runs` (C5) | 12 months | Purge prompt/output payloads; keep run metrics for reports (see **r5**) | Yes (payload) |
| `documents` / OCR text (C1–C3 mix) | Financial docs 7 years; raw OCR text 90 days | Delete GCS object + row past window; strip OCR text early | Yes, subject to financial legal-hold |
| `whatsapp_messages` (C4) | 18 months | Purge message bodies; keep conversation opt-in/opt-out state | Yes (opt-out state persists) |
| `email_logs` (outbox, C4) | 18 months | Purge body; retain delivery-status metadata | Yes |
| `notifications`/`tasks` | 12 months | Archive/purge | Yes (if personal) |
| Financial ledger (`payments`/`invoices`/`receipts`, C3) | 7 years | Retain; de-identify only via erasure | No (retain, de-link) |

Purge jobs write an `audit_logs` entry per batch (job id, class, dealer, row count) and are idempotent; a re-run over an already-purged window is a no-op.

## R10.7 Erasure propagation to backups / replicas (PENDING-INFRA)

- Live primary DB and read replicas within the app boundary are erased/anonymized synchronously by the saga.
- Propagation to **DR snapshots, off-site backups, and point-in-time recovery windows** depends on the backup/DR infrastructure, which is **PENDING-INFRA** (a pre-GA blocker, see **NC-12**/V4). Until it lands, the saga records a durable `pendingBackupErasure` marker per erased subject; when backup tooling is available the marker drives crypto-shredding / snapshot re-write. The spec does not claim backup erasure is live today.
- Encryption-at-rest and key-per-tenant crypto-shred (the eventual mechanism for irreversible backup erasure) are also PENDING-INFRA and tracked in V4, not asserted as production-ready.

## R10.8 RBAC, audit, entitlement & impersonation controls

- **RBAC (see **r4**, NC-5).** DSR operations bind to the `customers` module: `GET .../export` requires `customers:view` (typically elevated to `admin` for full-bundle export); `POST .../erase` requires `customers:admin` (destructive). Document deletion within the saga additionally respects `documents` module permissions. Field-level PII visibility in exports honors `role_field_permissions` (`hidden|view|edit`).
- **Entitlement gate (NC-9, INV-ENT-1).** The privacy/DSR feature passes through the entitlement/feature-flag gate *after* RBAC; if not entitled for the dealer, endpoints return `404` (hidden), enforced server-side, not merely in UI.
- **Audit (see **r4**).** Every export, erase, rectify, and consent change writes an `audit_logs` record (actor, subject id, action, class scope, dealer, timestamp, correlation/idempotency key). Erasure audit rows survive the erasure they describe.
- **Impersonation (NC-10).** Super-admin impersonation is READ-ONLY by default, time-boxed (≤60m), reason-logged, and stamped `impersonatedBy`. Under impersonation, `POST .../erase` and consent-affecting customer-sends are **HARD-BLOCKED** (erasure is a destructive customer-data write in the same protected class as money-posting/gate-resolution/customer-sends); read-only `export` is permitted for support. Writes require explicit elevation and are still blocked for the hard-blocked classes.
- **Kill-switch governance (NC-13).** Agent kill-switches that gate consent-aware agents are a platform-reserved *governance* capability — not grantable via `/admin/roles` and distinct from `settings:admin`.

## R10.9 Relationship to P3 whole-tenant offboarding

- **R10 = per-customer, LIVE tenant.** Rights here operate on one data subject while the dealer remains `active` (see **r2** dealers.status).
- **P3 = whole-tenant lifecycle.** Offboarding/closure moves `dealers.status: active → suspended → offboarding → closed`. In `suspended`, data-plane writes (including erase/rectify) return `423` while reads/exports remain available. `offboarding` triggers bulk export-then-purge of the entire tenant estate as a saga (NC-11), superseding individual DSR queues; `closed` is terminal.
- A per-customer erasure requested against a tenant already in `offboarding` is folded into the tenant-wide purge rather than executed independently.
- Both paths converge on the same PENDING-INFRA backup-propagation dependency (§R10.7).

## R10.10 Invariants

- **INV-PRIV-1.** Erasure anonymizes C1/C2 and de-links C3 but NEVER deletes financial ledger rows; the `payments` ledger stays immutable (reversal = offsetting entry).
- **INV-PRIV-2.** `audit_logs` are exempt from data-subject erasure and survive the subject they reference.
- **INV-PRIV-3.** WhatsApp/marketing opt-out is enforced at send time server-side; no outbound marketing (incl. A7 `outreach`) reaches an opted-out subject.
- **INV-PRIV-4.** DSR endpoints are dealer-scoped; a foreign-tenant customer yields `404`, never `403` (no existence leak).
- **INV-PRIV-5.** Erasure of external objects (GCS) runs in a saga step outside any DB transaction (NC-11); a `pendingBackupErasure` marker is durable until backup infra propagation completes.
- **INV-ENT-1 (ref NC-9).** Privacy/DSR features unentitled for a dealer are hidden with `404`, enforced server-side.
