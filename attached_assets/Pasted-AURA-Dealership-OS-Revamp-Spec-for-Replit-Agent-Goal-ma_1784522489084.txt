AURA Dealership OS — Revamp Spec (for Replit Agent)
Goal: make AURA read as a trustworthy, premium Dealer Management System the moment a customer opens it — deeper information, calmer denser layouts, an insights screen that drives action, an explicit review-and-approve gate between every pipeline stage, and a new trust-and-richness color system.

How to use this doc: work top to bottom. Each work item (WI-#) has What / Where / How / Done-when. Do NOT change API contracts unless a WI says so. Restart the artifacts/api-server workflow after any route change. Keep light + dark mode working and no emojis in the UI.

Global constraints (do not break)
Contract-first: any new endpoint goes in lib/api-spec/openapi.yaml first, then pnpm --filter @workspace/api-spec run codegen, then implement route + use generated hooks.
RBAC: every new mutating route runs through requireAuth → authorize → auditTrail and filters/stamps dealerId (see middlewares/rbac.ts).
Theme tokens only: never hardcode brand colors in components. Use text-primary, bg-primary, text-gold, etc. (Tailwind v4: a bg-x utility only works if --color-x is registered in the @theme inline block of index.css.)
Keep semantic colors: success = emerald, warning = amber, error/destructive = red. Only the brand red becomes sapphire. Do not turn error states blue.
Preserve the light/dark toggle and all existing :root.light override behavior.
1 · Color system — "Sapphire + Champagne Gold" (trust + richness)
Decision: replace blood-red brand with royal sapphire (primary, = trust/safety) and add champagne gold (accent, = richness/premium). Black + white stay. Red is retained only for destructive/error.

2 · Density & layout system (compact + list view — "these are too big")
Two problems the customer sees: cards/rails are oversized, and there's no way to scan as a list. Build ONE reusable system and apply it everywhere lists/cards appear.

WI-2.1 — useViewMode hook + ViewControls component
Where: new artifacts/aura/src/hooks/use-view-mode.ts and artifacts/aura/src/components/view-controls.tsx How:

useViewMode(pageKey: string) returns { density, setDensity, layout, setLayout }.
density: "comfortable" | "compact" — persisted in localStorage key aura-density (global, shared across pages).
layout: "grid" | "list" — persisted per page in aura-view:<pageKey>.
Defaults: density = "compact", layout = "grid" (compact is the new default — the current sizing becomes "comfortable").
<ViewControls> renders a small segmented control on the right of each page's command row: a Grid/List toggle (lucide LayoutGrid / List) and a Density toggle (lucide Rows3 / Rows2). Match the existing pill styling; sapphire active state. Done-when: toggles persist across reloads and page navigation.
WI-2.2 — Apply to every card/list surface
Add <ViewControls> + honor density/layout on: pages/customers.tsx (Account Portfolio), pages/inventory.tsx, pages/leads.tsx (Pipeline), pages/deals.tsx, pages/finance.tsx lists, pages/service.tsx, pages/parts.tsx. Rule: grid = cards (compact by default), list = dense table rows (~44–48px tall, text-sm, one row per record). Comfortable density = today's larger sizing.

4 · Stage-gate review checks (the "review & approve to next stage" the client wants)
Today advancement happens via side-effects or a free status dropdown, with only cosmetic checkmarks (lead-workflow-dialog.tsx) and no gate. The delivery workflow (routes/deliveries.ts) is the ONLY real gated flow — use it as the model for the whole pipeline.

WI-4.1 — Define entry/exit criteria per stage
Implement these as the checklist shown before advancing. Advancement is blocked (button disabled + reason) until required items pass; the "Sold" transition additionally needs a manager approval.

Advance to	Required checklist	Approver
Qualified	Contact made · budget/financing captured · purchase intent set · vehicle of interest set	Advisor
Test Drive	Vehicle available · driver's licence + signed waiver captured · slot booked	Advisor
Negotiation (was "Desking")	Test drive done or explicitly waived · trade-in appraised or "no trade" · draft numbers entered	Advisor
Sold	Deposit taken · finance approved OR cash verified · discount within floor (else raises below_floor_price gate) · vehicle locked to VIN	Manager
In Prep → Delivered	already gated in routes/deliveries.ts — leave as-is	Delivery / QC
WI-4.2 — "Advance stage" gated action
Where: components/lead-workflow-dialog.tsx + new endpoint. How:

Add POST /leads/{id}/advance (openapi first). Body: { toStage }. Server validates the checklist for toStage; returns 422 { unmet: [...] } if criteria fail; on success sets phase/status, writes a timeline event (stage_advanced, actor = signed-in user), and stamps stageEnteredAt (WI-4.4).
In the dialog, replace the free Status dropdown (currently any→any) with a Review & Advance panel: render the target-stage checklist with pass/fail ticks (reuse the SectionCard done styling) and a primary "Approve → Advance to X" button, disabled with a reason chip until all required items pass. Done-when: you cannot set a lead to a later stage while required items are unmet; every advance is logged with who approved it.
WI-4.3 — Manager approval on "Sold" + unified Reviews inbox
Where: routes/deals.ts, pages/approvals.tsx, components/gate-card.tsx How:

Guard deal stage transitions in PATCH /deals/:id with an allowed-transition map (mirror VEHICLE_STATUS_TRANSITIONS); reject out-of-order jumps 422.
Advancing a deal to committed/sold with a discount below floor creates a below_floor_price gate (already a type) requiring manager approval; block commit until resolved.
Rename the Approvals page to "Reviews" and show BOTH exception gates AND pending stage-advance reviews awaiting the current user, grouped (Needs your approval / Exceptions). Done-when: a rep cannot self-approve a below-floor discount to Sold; a manager sees it in Reviews.
WI-4.4 — Track time-in-stage
Where: lib/db/src/schema/leads.ts (+ deals if useful), codegen, routes. How: add nullable stageEnteredAt timestamptz; set it on every advance. Expose in list responses. Powers "Days in stage" and SLA chips (WI-3.3) and the landing action queue (WI-5). Run pnpm --filter @workspace/db run push (dev).

WI-4.5 — Add the missing controls (from prior analysis)
Vehicle VIN lock: creating/committing a deal sets the vehicle status available → reserved (and → booked on commit); block a second deal on a reserved/booked VIN (422). Use the existing VEHICLE_STATUS_TRANSITIONS.
Deposit gate: reservationFeePaid/depositPaid must be true before Sold.
Test-drive licence + waiver: capture licence number + a waiver-accepted flag on both the staff POST /leads/:id/test-drive and the public booking flow before confirming.

8 · Acceptance criteria (definition of done for the whole revamp)
App is sapphire + gold in both light and dark; only errors are red; nothing looks red-branded.
Every list/card page has a working, persisted Grid/List + Compact/Comfortable toggle; compact is default; cards are visibly smaller.
Account Portfolio and the Pipeline rail are compact; both have a usable list/table view.
The Pipeline rail is a slim chevron; lead rows show owner, last activity, days-in-stage, value, next action; a full-pipeline table exists.
Advancing a lead/deal requires a visible review checklist; required items block the "Approve → Advance" button; below-floor discounts need manager approval; every advance is logged with the approver.
Vehicle VIN cannot be double-sold; deposit required before Sold; licence + waiver captured before a test drive.
Landing leads with a prioritized Action Queue whose buttons work; KPI cards deep-link.
Journey + Appraisals removed; Insurance removed from Finance (kept in Delivery); "Desking"→"Negotiation", "In Prep"→"Pre-Delivery" everywhere.
pnpm run typecheck passes; api-server restarted; light/dark both verified; no emojis.

1 (color) → 2 (density/list system) → 3 (pipeline) → 7 (wording) → 6 (removals) → 4 (stage gates + controls) → 5 (action queue). Colors and the density system first so every later screen inherits them.
