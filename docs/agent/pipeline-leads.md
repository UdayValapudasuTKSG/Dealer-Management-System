# Pipeline, Leads & Deals

## Pipeline page (`pages/leads.tsx`, routes `/pipeline` + `/leads`)
- NO kanban columns. A slim clickable chevron 8-stage rail (DMS-spec phases): New → Contacted → Engaged → Pre-Book → Vehicle Allocated → Payment → Pre-Delivery → Delivered (labels only — underlying phase/stage values unchanged, NO DB migration). Pre-sale stages map 1:1 from lead phase (`aware/consider/engage/negotiate`); `won` leads split into Vehicle Allocated / Payment / Pre-Delivery / Delivered by their furthest-along linked deal (delivered > committed > finance > other; matched by `deal.leadId`, fallback `customerId`) via `stageOf` (needs `useListDeals`).
- Selecting a stage shows that stage's lead list plus an "AURA recommends" panel auto-fetching `useGetPipelineSuggestions({ phase })` with loading/error/retry states. Suggestions pass the underlying phase (`won` for the last three stages).
- Full-pipeline list table (search/stage filter/sort, deal value per lead, NEXT_ACTION hints, days-in-stage from `stageEnteredAt`).
- On the Deals page the `desking` deal stage is labelled "Desking" (deals also has a separate `negotiation` stage — both as "Negotiation" collided).
- Pipeline AI endpoint: `GET /pipeline/suggestions?phase=` (`routes/pipeline.ts`, Anthropic via `@workspace/integrations-anthropic-ai`, returns `{phase,label,count,headline,actions[]}`, 502 on LLM failure). Contract: `PipelineSuggestions`/`PipelineSuggestionAction` in openapi.yaml.

## Stage advance gates (2026-07 revamp)
- Lead stage advances go through `POST /leads/{id}/advance` with requirement gates — 422 returns `unmet[]`, shown in the Workflow dialog "Review & Advance" section. Every advance stamps `stageEnteredAt` and writes a `stage_advanced` timeline event.
- Gates are CONFIG-DRIVEN: per-dealer per-stage versioned checklists (`stage_checklists` table, `lib/db/src/schema/stageChecklists.ts` defaults = v0). `getActiveChecklist` (`api-server/src/lib/stage-checklists.ts`) picks the latest version; the advance route runs only ENABLED items (key→check map in `routes/leads.ts`), unmet messages use configured labels. Edited at Settings → Stage Checklists (`GET/PUT /admin/stage-checklists[/{stage}]` — each PUT publishes version+1; stages: qualified/test_drive/negotiation/sold).
- Lead sources are config-driven too: dealer-scoped `lead_sources` (lazy-seeded defaults, `api-server/src/lib/lead-sources.ts`); `GET /leads/sources` feeds the New Lead form dropdown; sources flagged `isSocial` REQUIRE `sourceDetail` (facebook/instagram/tiktok/youtube/whatsapp/other) — POST /leads 422s without it. Admin CRUD at Settings → Lead Sources (`/admin/lead-sources`).
- Per-dealer tax rules: `dealer_taxes` (percent|fixed, optional threshold, effectiveFrom, sortOrder; lazy-seeded VAT/duty/excise defaults) managed at Settings → Taxes (`/admin/taxes` CRUD). Deterministic config only — quote-side tax application is downstream.
- Deal stage transitions in `PATCH /deals/:id` are guarded by an allowed-transition map; out-of-order jumps 422. Deposit required before Sold; VIN double-sell blocked; licence + waiver captured before test drive; below-floor discounts need manager approval (Reviews).
- There is NO standalone approvals/reviews page (removed 2026-07). Pending gates render as actionable GateCards inline on the record they concern: `stage_advance` in the lead workbench's Action Chain, deal gates on Deals, finance gates on Finance, customer gates on the customer overview; dashboard triage deep-links each gate to its record (`gateHref` in `lib/triage.ts`). The `approvals` RBAC module still gates who can see/resolve them.
- `components/action-queue.tsx` ("Your day" ranked queue, cap 6) mounts on Pipeline + dashboard; dashboard KPI cards deep-link (deals/pipeline/tasks).

## Lead detail (`pages/lead-detail.tsx`, route `/lead/:id`)
- Salesforce-parity record page: header badges + AI score + Workflow dialog; `StageNav` is a HORIZONTAL full-width Journey pane on TOP of the two-column layout (8-phase stepper + current-stage success-guidance checklist, `components/lead/stage-nav.tsx`, derived from lead fields + furthest linked deal); left rail (Key Fields / `AgentBriefPanel` AI next-best-actions (`components/lead/agent-brief.tsx`, `GET /leads/{id}/agent-brief` — Anthropic-backed risk level, actions, draft follow-up with copy + WhatsApp deep link) / per-status Guidance for Success / vehicle card), tabs Details / Quotes & Files / Activity (post-note box).
- Details tab = 8 collapsible sections; ALL fields inline-editable via `InlineField` (pencil-on-hover; text/textarea/date/checkbox/select; gated `can("leads","edit")`; PATCH via `useUpdateLead` typed against `LeadUpdate`). Every editable field MUST exist in `LeadUpdate` in openapi.yaml or Zod strips it server-side and the PATCH 500s with "No values to set"; never cast the patch `as never`.
- status/phase stay read-only (Workflow dialog); isRetailCustomer displays `stored||!!customerId`; quotationSent displays `stored||!!quote?.sentAt`. 15 SF-parity lead columns (company, title, isRetailCustomer, quotationSent, reservationFeePaid, reservationComments, financingQualified, contactedDate, revisitIn3Months, closureReason, purchaseIntent, keyInterestDriver, budgetFinancing, description, address).
- Lead Owner links to `/team/:id` (`pages/team-profile.tsx`; `GET /team/{id}` in `routes/team.ts` — profile + lead stats + recent leads, no testDriveToken leak); vehicle card links to `/vehicle/:id`. Header "Edit" dialog (`editLeadFields()`) for bulk edits.
- Server: `POST /leads/{id}/notes` (timeline note, actor = signed-in user); `GET /leads/{id}/quote` + `/quote.pdf` — quote regenerates the exact emailed PDF by reusing the `vehicle_quote` email payload from `email_logs` (matched via `quoteRef LIKE 'Q-<id>-%'`); never-emailed leads with a vehicle get a fresh quote dated today.
- WhatsApp tab (only `source === "whatsapp"` leads): chat-bubble transcript (`components/lead/whatsapp-panel.tsx`, 15s poll). `GET /leads/{id}/whatsapp` returns `{messages,canReply,replyBlockedReason,windowExpiresAt}`; `POST /leads/{id}/whatsapp` sends a staff reply — only inside the 24h service window after last inbound, 422 otherwise, logs a `whatsapp_message` timeline event.

## Lead capture & auto-assignment
- Lead capture is inventory-locked: vehicle selection is a MANDATORY dropdown in both lead forms (no free text). Public enquiry form uses `useListEnquiryVehicles` (`GET /enquiries/vehicles`, public) and submits `vehicleId`; `POST /enquiries` 422s on unknown id (any status accepted on purpose) and derives variant/color from inventory. Internal New Lead dialog requires `interestedVehicleId` and derives variant/color in onSubmit.
- Auto-assignment: every new lead (staff POST /leads, public /enquiries, webhook intake) runs `autoAssignLead` (`lib/lead-assignment.ts`) — least-loaded active Sales Advisor (fallback incl. Sales Manager) by open-lead count; sets ownerUserId/assignedTo, status new→assigned, phase aware→consider (race-guarded on `owner_user_id is null`); logs `advisor_assigned` timeline + activity as "AURA Sales Agent"; bumps agents.tasksToday; notifies the advisor; emails a `lead_assignment` intro. Never throws — unassignable leads stay `new`. Manual `POST /leads/:id/assign` overrides.
- Customer detail (`pages/customer-detail.tsx`) shows a read-only "Journey Stage" stepper derived from the client's furthest lead phase and deal stage (desking/negotiation/finance/committed→Desking, delivered→Delivered).

## Self-service test-drive booking
- Every lead has a `testDriveToken` (uuid, unique, DB default). On lead/enquiry creation `onLeadCreated` emails a `test_drive_invite` (CTA `https://<REPLIT_DOMAINS first || REPLIT_DEV_DOMAIN>/book-test-drive/<token>`, skipped when a drive is already scheduled).
- Public page `pages/book-test-drive.tsx` (route OUTSIDE AppShell) + public API `routes/test-drive.ts` (mounted before requireAuth): `GET /test-drive/{token}` returns 14 days of hourly slots (9 AM–4 PM server-local, starting tomorrow); `POST /test-drive/{token}/book` blocks the slot (one drive at a time across ALL leads — 409 conflict, 422 off-grid, 404 bad token), sets testDriveAt/branch/status test_drive/phase→engage, timeline event, `test_drive_confirmation` email, owner-or-coordinator notification; rebooking = reschedule. Staff route `POST /leads/:id/test-drive` enforces the same exact-time 409.
- Click-to-call: `components/lead/call-dialog.tsx` + telephony seam `api-server/src/lib/telephony.ts`. With the full Twilio Voice credential set (`TWILIO_ACCOUNT_SID`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET`, `TWILIO_TWIML_APP_SID`, `TWILIO_PHONE_NUMBER`, `TWILIO_AUTH_TOKEN`) advisors dial from the browser (Twilio Voice JS SDK): `POST /telephony/token` mints an access token, the TwiML App's Voice URL must point at `POST /api/webhooks/twilio/voice` (creates the `call_logs` row, status `in_progress`, returns `<Dial>`), and the `<Dial action>` callback `/api/webhooks/twilio/voice/complete` stamps duration + outcome automatically (DialCallStatus mapped via `mapTwilioDialStatus`; failed/canceled → no_answer). Notes/sentiment attach afterwards via `PATCH /leads/{id}/calls/{callId}`. Without creds `GET /telephony/config` reports `stub` and the dialog falls back to manual dial + log. Webhooks are Twilio-signature-verified.
- Call recording + transcription (2026-07): the voice `<Dial>` sets `record="record-from-answer-dual"` with `recordingStatusCallback` → `POST /api/webhooks/twilio/voice/recording?callLogId=N` (signature-verified) which stamps `recordingSid`/`recordingUrl` on `call_logs`, sets `transcriptStatus=pending`, and fires `autoTranscribeCall` (`lib/call-transcription.ts`): downloads the .mp3 via Twilio Basic auth, runs OpenAI speech-to-text (`@workspace/integrations-openai-ai-server/audio`), stores `transcript` (`transcriptStatus` none→pending→done/failed), then re-runs `autoAnalyzeCall` so sentiment uses the REAL conversation (transcript is included, sliced to 6k chars, in the untrusted context of `call-analysis.ts`). Playback is proxied — `GET /leads/{id}/calls/{callId}/recording` streams audio/mpeg tenancy-scoped (raw Twilio media URL never reaches the client); the lead Correspondence → Calls cards render an `<audio>` player + collapsible transcript with pending/failed states.
- BOTH booking paths call `ensureAccountForLead` (`lib/accounts.ts`) right after the update: a booked test drive promotes the lead to an account — matches an existing customer by lower(email)/phone digits, else creates one (tags `["test-drive"]`), links `leads.customerId`, logs `account_created`/`account_linked`; never throws.
- Calendar invites (`lib/calendar.ts`): string-only calendar fields ride in the email payload jsonb; `processQueue` attaches a nodemailer `icalEvent` (METHOD:REQUEST .ics) to `test_drive_confirmation` (customer) and `test_drive_owner_invite` (lead owner, needs `users.email`). UID stable per lead; `calSequence` (epoch seconds) bumps on rebooking so calendar clients UPDATE the same event instead of duplicating. The `vehicle_quote` email also carries the booking CTA link when no drive is booked yet.

## Call test-drive intent agent (2026-07)
- The call sentiment pass (`api-server/src/lib/call-analysis.ts`, one Claude call) ALSO extracts test-drive intent: `{testDriveIntent, testDriveTime ("YYYY-MM-DDTHH:mm" Guyana local, null unless explicitly stated), testDriveTimeConfidence, testDriveVehicle}`. The prompt carries "Now (Guyana time)" so relative dates resolve; the model must NEVER invent a time. Intent handling is transcript-gated and runs even when the sentiment confidence gate holds the score.
- Orchestration in `api-server/src/lib/test-drive-intent.ts` (`handleTestDriveIntent`). Deterministic guardrails: time confidence ≥ MIN_AGENT_CONFIDENCE, parseable, ≥30min in the future, ≤30 days out, hour 9–16 (Guyana, matching the public booking window). Clear time + available vehicle + free slot → auto-book (`test_drives.bookedVia="agent"`, lead testDriveAt/status update WITHOUT a phase jump, ensureAccountForLead, afterTestDriveBooked soft-lock + 24h reminder), then `test_drive_confirmation` email with the .ics calendar fields + WhatsApp confirmation with reschedule link + owner notification, then ONE checklist-gated auto-advance (same `getActiveChecklist`/`buildStageChecks` rules as POST /leads/{id}/advance — never skips, unmet items logged to the timeline instead).
- Any other outcome (vague/past/off-hours/low-confidence time, vehicle unavailable, slot conflict) → tokenized self-service selection link on every channel the lead has + advisor "time needed" notification. Existing upcoming drive → never duplicate; reschedule link referencing the current booking. Call with no live lead → event logged on the call only.
- Idempotent per call: the `agent_runs` row (runType `test_drive_intent_auto`) is keyed refType `call_log`/refId call id — NEVER override refType per outcome or transcription retries re-run the agent (leads live in `affectedEntities` instead). Outbox messages use dedupeKey `tdintent:{callId}:*`. Kill-switch: the whole analysis pass requires `isAgentEnabled(dealer,"sales",{strict:true})`.
